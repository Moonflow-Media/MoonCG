# Extensions

An extension is the server-side part of a bundle: an ES module whose default export MoonCG calls
once when the bundle starts.

```js
// extension/index.js
export default async function start(ctx) {
  const score = ctx.replicant('score');
  await score.ready;

  await ctx.handle('reset', async () => {
    await score.set({ home: 0, away: 0 });
    return score.value;
  });
  await ctx.http.get('/score', () => ({ body: score.value }));

  ctx.onDispose(() => ctx.log.info('Stopped'));
}
```

The manifest names the file and what the extension may reach:

```json
{
  "extension": "extension/index.js",
  "capabilities": ["http.routes"],
  "messages": { "reset": { "send": "operate" } }
}
```

An extension can import `@mooncg/sdk/extension` without installing anything: the server
provides its own copy, in step with its protocol. If the bundle has a copy of `@mooncg/sdk` in
its `node_modules`, the server's copy is used all the same. An extension never needs
`@mooncg/core`.

```js
import { MoonCGError } from '@mooncg/sdk/extension';
```

For types, install `@mooncg/sdk` as a development dependency and annotate the function:

```ts
import type { ExtensionMain } from '@mooncg/sdk/extension';

const start: ExtensionMain = async (ctx) => {
  /* ... */
};
export default start;
```

A `mooncg-env.d.ts` generated by `mooncg types` types `ctx.replicant('score')` as well.

## How an extension runs

Each extension runs in its own worker thread. That has three consequences:

- **Everything that reaches the server is asynchronous.** The extension has no direct access to
  the server's state; it talks to the server like a page does, over the same protocol.
- **An extension cannot take the server down.** An uncaught exception, an unhandled promise
  rejection, a `process.exit()`, an endless loop or running out of memory ends the extension's
  thread only. The bundle becomes `failed` with the error; the server and the other bundles
  keep running.
- **Stopping is clean.** When the thread ends, its timers, sockets and listeners end with it,
  and the server forgets everything the extension had registered.

The default export is done when its promise resolves; only then is the bundle `running`. If it
throws or rejects, the bundle is `failed` and nothing it wrote to persistent replicants is kept.

## The context

| Member                                            | What it is                                                                                              |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `ctx.bundle`                                      | `{ name, version }` from the manifest                                                                   |
| `ctx.log`                                         | `info(message)`, `warn(message)`, `error(message)`; lines appear in the server log as `[bundle:<name>]` |
| `ctx.config`                                      | The bundle's configuration. An empty object for now                                                     |
| `ctx.replicant(name)`                             | A replicant handle, the same as in a page                                                               |
| `ctx.send`, `ctx.on`, `ctx.request`, `ctx.handle` | Messages                                                                                                |
| `ctx.http`                                        | HTTP routes                                                                                             |
| `ctx.onDispose(fn)`                               | Cleanup when the extension stops                                                                        |

### Replicants

```js
const score = ctx.replicant('score'); // 'other-bundle:name' reaches another bundle
await score.ready; // the first value has arrived
score.value; // a frozen snapshot
score.subscribe((value, meta) => {}); // now and on every change; returns an unsubscribe
await score.set({ home: 0, away: 0 }); // replace; last write wins
await score.update((draft) => {
  // change; re-run on a conflict, up to three times
  draft.home++;
});
```

Replicants are declared in the manifest, not in code. A write that the schema rejects fails with
the code `invalid`.

### Messages

A message is declared in the manifest under `messages` and named `bundle:name`; inside its own
bundle the bare name is enough.

```js
await ctx.send('goal', { side: 'home' }); // to everyone listening
const stop = await ctx.on('goal', (data, { sender }) => {});
const answer = await ctx.request('team-data:lookup', { id: 7 }, { timeout: 2000 });
await ctx.handle('reset', async (data, { sender }) => 'done');
```

- `send` reaches the listeners of that one message, pages and extensions alike. There is no
  broadcast to everyone.
- `request` asks the single handler of a message and resolves with what it returns. It rejects
  with `not_found` when nobody handles the message, `timeout` after 5 seconds (or the `timeout`
  given, at most 60 seconds), `unavailable` when the handler's bundle stops first, or with the
  error the handler raised.
- `handle` answers requests. Only extensions can, and only for messages of their own bundle. A
  message has one handler. Throw a `MoonCGError` (from `@mooncg/sdk/extension`) to reject with a
  code of your choice; anything else reaches the caller as `internal`, and the details go to
  the log.
- `sender` is `{ principal, bundle }`: who sent it, and from which bundle's page or extension.
- Data is JSON, with the same limits as replicant values.
- The manifest's `send` and `listen` permissions decide who may send or request, and who may
  listen. They apply to pages; an extension is limited by its capabilities instead.

Pages have `mc.send`, `mc.on` and `mc.request` with the same meaning. Pages cannot `handle`.

### HTTP routes

Routes live under `/b/<bundle>/api`. Registering them needs the capability `http.routes`.

```js
await ctx.http.get('/teams/:id', (request) => ({ body: { id: request.params.id } }));
await ctx.http.post(
  '/goal',
  async (request) => {
    const { side } = request.json();
    return { status: 201, body: 'ok' };
  },
  { permission: 'operate' },
);
```

- Methods: `get`, `post`, `put`, `patch`, `delete`. A path is `/` or segments of literal text
  and `:name` parameters.
- The handler gets `{ method, path, params, query, headers, body, text(), json() }`. `body` is
  the whole body as a `Uint8Array`, at most 1 MiB unless the server is configured otherwise.
  `json()` fails the request with status 400 if the body is not JSON.
- It returns `{ status?, headers?, body? }`. A string body is sent as text, a `Uint8Array` as
  bytes, anything else as JSON; `status` defaults to 200.
- A caller needs the bundle's `access` permission, or the manifest permission named in
  `permission`.
- A handler that returns nothing answers an empty 200. Anything that is not such an object, a
  status outside 200 to 599, a body that is not JSON, or a header with a line break in it
  answers 500.
- Headers that describe the connection (`connection`, `transfer-encoding`, `content-length`
  and the like) are dropped; the server sets them.
- `HEAD` is answered like `GET`, without the body. A trailing slash is ignored. A path that
  exists under another method answers 405 with an `Allow` header; so does `OPTIONS`.
- Two patterns that differ only in their parameter names, such as `/u/:id` and `/u/:name`,
  cannot both be registered. Where several patterns fit a path, the one with more literal
  segments wins, then the one registered first.
- A handler that throws answers 500 without details; one that does not answer within 10 seconds
  answers 504; when the bundle stops while a request is under way, 503.
- Requests that change something (anything but `GET` and `HEAD`) are only accepted from pages
  of this server or of an allowed origin, and from clients that send no `Origin` at all.
- Responses are not streamed.

To answer with a client error, throw a `MoonCGError`:

```js
import { MoonCGError } from '@mooncg/sdk/extension';

await ctx.http.get('/teams/:id', (request) => {
  const team = teams.get(request.params.id);
  if (!team) throw new MoonCGError('not_found', `No team ${request.params.id}`);
  return { body: team };
});
```

| Code                     | Status               |
| ------------------------ | -------------------- |
| `bad_request`, `invalid` | 400                  |
| `forbidden`              | 403                  |
| `not_found`              | 404                  |
| `conflict`               | 409                  |
| `unavailable`            | 503                  |
| `timeout`                | 504                  |
| anything else thrown     | 500, without details |

The same error thrown from a `handle` callback reaches the caller of `request` with its code
and message. A handler that returns nothing answers `null`.

### Cleanup

`ctx.onDispose(fn)` registers cleanup. Callbacks run in reverse order when the bundle is
disabled or reloaded, or the server shuts down. They have two seconds together; then the thread
is ended regardless. They do not run when the extension crashes.

## Capabilities

`capabilities` in the manifest is what the extension asks for beyond its own bundle. Without
the capability the call is rejected with `forbidden`.

| Capability            | Allows                                                              |
| --------------------- | ------------------------------------------------------------------- |
| `bundle:<name>:read`  | Reading replicants of bundle `<name>` and listening to its messages |
| `bundle:<name>:write` | Writing its replicants and sending it messages and requests         |
| `http.routes`         | Registering HTTP routes                                             |

`<name>` may be `*`. Capabilities limit the extension; permissions limit the people using the
bundle. Bundles are still trusted code: a worker thread is isolation against accidents, not a
sandbox.

To use another bundle, also list it under `dependencies` with a version range. MoonCG starts a
bundle after its dependencies, refuses to start it if one is missing, has the wrong version or
is not running, and refuses to disable a bundle that running bundles depend on. Reloading a
bundle restarts the bundles that depend on it. When a bundle crashes, the bundles that depend
on it are stopped and started again once it is back.

## Limits

An extension shares the machine with the show, so the server keeps it within bounds. One that
goes beyond them is ended and treated as crashed.

| Limit                                             | Default                        | Setting                            |
| ------------------------------------------------- | ------------------------------ | ---------------------------------- |
| Time to start (until the default export resolves) | 10 s                           | `--extension-start-timeout-ms`     |
| Time without answering the server's heartbeat     | 10 s                           | `--extension-heartbeat-timeout-ms` |
| Heap memory                                       | 256 MiB                        | `--extension-memory-mb`            |
| Size of one message to the server                 | 1 MiB                          | fixed                              |
| Log lines                                         | 100 lines or 64 KiB per second | fixed                              |
| Requests waiting for its answer                   | 100                            | fixed                              |
| Messages to the server, of any kind               | 10,000 per second              | fixed                              |

- **Do not compute for long without a break.** The server asks every extension for a sign of
  life every five seconds, and the extension can only answer between two pieces of work. About
  ten seconds of uninterrupted synchronous work get it restarted. Split long work up, with an
  `await` in between, or do it in a worker of your own.
- Log lines over the limit are dropped; the log then says how many.
- Once 100 requests wait for the extension's answer, further ones fail as `unavailable` (503
  over HTTP) until it catches up.

## When an extension fails

| What happens                                                      | Result                                                                                                                                                          |
| ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A start that was asked for fails (at boot, by enable, by reload)  | Bundle `failed`; not retried                                                                                                                                    |
| A running extension crashes                                       | Bundle `failed`, then restarted after 1 s, 2 s and 4 s. A start that fails during such a restart counts as one of the three. After three it stays `failed`      |
| It has run for a minute since a restart                           | The count of restarts starts over                                                                                                                               |
| An administrator enables, disables or reloads it                  | Pending restarts are dropped                                                                                                                                    |
| A bundle it depends on crashes                                    | It is stopped (`failed`, with an error naming that bundle) and started again when that bundle is back. If that bundle is not restarted again, it stays `failed` |
| It does not start again after a bundle it depends on was reloaded | It stays `failed`, not retried; the error says that the restart followed that reload                                                                            |

A failed bundle exposes nothing: no replicants, messages, routes or files. Its last error is
shown in the dashboard and in `GET /api/v1/bundles`.

## Coming from NodeCG

NodeCG extensions run inside the server process and get a synchronous API. MoonCG extensions
run in a worker thread, so the same things are asynchronous.

| NodeCG                                                        | MoonCG                                                                                                            |
| ------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `module.exports = (nodecg) => { ... }`                        | `export default async function start(ctx) { ... }`                                                                |
| `const rep = nodecg.Replicant('score', { defaultValue })`     | Declare `score` with its `default` in `mooncg.json`; `const rep = ctx.replicant('score'); await rep.ready;`       |
| `rep.value.home++` (assignment is sent)                       | `await rep.update((draft) => { draft.home++; })`                                                                  |
| `rep.value = next`                                            | `await rep.set(next)`                                                                                             |
| `rep.on('change', (newValue, oldValue) => {})`                | `rep.subscribe((value, meta) => {})`                                                                              |
| `nodecg.sendMessage('reset', data)`                           | `await ctx.send('reset', data)`                                                                                   |
| `nodecg.listenFor('reset', (data, ack) => ack(null, result))` | `await ctx.handle('reset', async (data) => result)` for an answer, `await ctx.on('reset', (data) => {})` for none |
| `nodecg.sendMessage('reset', data, callback)`                 | `const result = await ctx.request('reset', data)`                                                                 |
| `nodecg.Router()` + `nodecg.mount(router)`                    | `await ctx.http.get('/path', handler)` under `/b/<bundle>/api`                                                    |
| `nodecg.bundleConfig`                                         | `ctx.config` (empty for now)                                                                                      |
| `nodecg.log.info(...)`                                        | `ctx.log.info(...)`                                                                                               |
| `nodecg.extensions['other-bundle']`                           | Not available. Use the other bundle's replicants and messages, with a capability                                  |

Before and after, for a reset button:

```js
// NodeCG
module.exports = (nodecg) => {
  const score = nodecg.Replicant('score', { defaultValue: { home: 0, away: 0 } });
  nodecg.listenFor('reset', (_data, ack) => {
    score.value = { home: 0, away: 0 };
    ack(null, score.value);
  });
};
```

```js
// MoonCG
export default async function start(ctx) {
  const score = ctx.replicant('score');
  await ctx.handle('reset', async () => {
    await score.set({ home: 0, away: 0 });
    return score.value;
  });
}
```

Three habits to change:

1. **Await writes.** `set` and `update` resolve when the server has committed the change, and
   reject if it refused. A forgotten `await` hides the rejection.
2. **Do not mutate `value`.** It is frozen. Change it through `update`.
3. **Do not share objects between bundles.** There is no `nodecg.extensions`. What another
   bundle should see goes into a replicant or a message.
